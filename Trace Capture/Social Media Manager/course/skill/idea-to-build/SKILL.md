# Idea to Build

Use this workflow to carry the user's intent from an idea to an actionable, verifiable outcome. Adapt the depth to the request and the risk. Honor the user's current stage, choices, authorization, and governing project instructions; do not restart an already agreed process, reopen settled decisions without evidence, or require an extra approval where the user has already authorized the work.

## Start at the right stage

1. Establish the requested outcome, current stage, applicable authority, and existing evidence. Inspect relevant project instructions and source documents before treating assumptions as facts.
2. For an early or unclear idea, capture the user's intent before proposing a design. If they are still providing context, let them finish. Mirror the goal, people, observable journey, constraints, facts, assumptions, unknowns, contradictions, and non-goals. When the user requests an alignment gate, wait for agreement before architecture.
3. Research existing reality and resolve only decisions that materially affect scope, architecture, risk, or cost. Record choices and why they were made. Avoid treating planned behavior as deployed behavior.
4. Model the architecture and workflows, then turn the agreed design into a build specification, measurable acceptance criteria, and dependency-aware plan. Document only what the project needs, following existing conventions.
5. When implementation is authorized, execute the approved scope in small verifiable slices. Keep boundaries, tests, evidence, operations, and handoff aligned. Finish authorized independent work before reporting an exact blocker.

Use **plan → work → review → compound** to fit the task. Route deterministic work to tools, choose the cheapest capable available executor for bounded work, and reserve harder judgment and integration for a qualified lead. Do not claim unavailable tools, models, usage measurements, or integrations. Distinguish implemented, offline-tested, provider-accepted, and live-observed.

## Load details only as needed

- For discovery, decisions, architecture, or workflows, read [discovery-and-architecture.md](references/discovery-and-architecture.md).
- For specifications, acceptance, execution, proof, or a restartable handoff, read [spec-and-delivery.md](references/spec-and-delivery.md).
- For delegation, cost/usage controls, autonomous execution, or recovery, read [routing-and-autonomy.md](references/routing-and-autonomy.md).

The workflow is guidance, not an access-control mechanism. Respect the user's instructions and actual host permissions for spending, credentials, publishing, destructive actions, and external effects. A request to continue autonomously does not expand scope. If a required decision or permission is genuinely missing, identify it precisely and continue useful independent work.
