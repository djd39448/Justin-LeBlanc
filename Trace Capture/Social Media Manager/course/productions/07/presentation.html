LESSON 07

Coding standards and evidence

Evaluate code quality, verification, and proof claims.

Video · Transcript · Captions

Visual outline
  1. Standards are for the next reader: Judge whether another person can understand and change the software.
  2. A failed save must look like a failure: Compare the visitor’s impression with what actually happened.
  3. Test the edges of the system: Check where information enters, leaves, and changes state.
  4. A slice includes its proof: A saved revision is useful, but it is not proof by itself.
  5. Four observations, four different claims: Treat these as distinct evidence types, not an automatic ladder.
  6. Keep evidence and recovery inspectable: A review record should reveal both confidence and gaps.
  7. Make the code explain its purpose: Future diagnosis starts with names and responsibilities.
  8. Give the right person the right error: Visitor feedback and operator diagnostics serve different jobs.
  9. Prove the forbidden effects stay absent: A successful example cannot cover every important boundary.
  10. Where was the claim tested?: Match the environment to the observation.
  11. Review one coherent change: Ask focused questions while the change is small enough to assess.
  12. Write a record someone else can inspect: A useful evidence note contains context rather than confidence alone.
  13. Ask to see the observation: Replace broad quality claims with specific evidence.
