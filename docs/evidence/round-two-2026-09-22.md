## Contract and privacy evidence

- Public inquiry parsing accepts `email`, `text`, and `phone`; phone is required for text/phone
  preferences. `budgetCents` is an exact bounded integer-or-null field, while legacy `budget`
  records remain readable and resumable.
- Boundary tests prove visitor budget context cannot alter estimates, agreed quotes, invoices, or
  charge authorization. Dormant voice/chat adapters continue to send legacy budget values with
  `budgetCents: null` when absent.
- `PublicEventsCalendarReader` is isolated from booking/free-busy logic. It accepts only an exact
  private calendar ID from server configuration, uses read-only list calls, applies the 180-day,
  four-page, and 100-output bounds, coalesces refreshes, and caches only sanitized DTOs.
- Multi-calendar fixtures place private wedding, corporate, consultation, and hold records only on
  forbidden sources. Tests prove those sources are never queried and never appear in output.
- Mapping/failure tests cover timed confirmed events, recurrence identity, DST/cross-midnight
  instants, invalid provider envelopes, pagination overflow, timeouts, retry limits, fresh/stale
  cache behavior, successful empty results, and the fixed fail-closed 503 response.
- DTO assertions allow only opaque HMAC ID, bounded title/venue, optional controlled city,
  start/end, timezone, freshness status, and `lastUpdated`. Raw Calendar/event IDs, descriptions,
  attendees, organizer/email, conferencing, attachments, extended properties, private record IDs,
  source URLs, addresses, and money are absent.
- The public-output audit proves the built site contains no public chat/voice surface, phone number,
  `tel:` URL, package price, assistant marketing, or banned demo/engineering language. Dormant
  assistant implementation and backend tests remain present.
- Eight Pages-proxy tests prove that only an exact `GET /api/public-events` 503 with the fixed safe
  body is reconstructed with approved headers. Wrong bodies, non-GET requests, other API paths,
  and 500/502/504 responses stay behind the generic backend-unavailable envelope.

## Routing and external boundary

The main coding/release conductor retained architecture, security review, integration, and release
decisions. Bounded contract, adapter, web, browser, audit, and review work was routed to lower-cost
Luna/Terra workers and independently rerun by the conductor. Account usage moved from 50% to 52%;
the available reset credit was not used.

Switchboard workers were unavailable, so the conductor used the already-authorized SSH path to the
exact Windows host after matching its saved host-key fingerprints. All provider checks and release
actions stayed within the isolated Justin resources. The deployment changed the runtime checkout,
added only the fail-closed public-events flag to protected configuration, restarted the three owned
tasks, and published the Pages bridge. It did not create/edit/share a Calendar or event, broaden
OAuth, change DNS/Retell/mail/billing, send customer communication, or reset SQLite.

## Remaining release gates

1. Owner-confirm an exact public-performance-only Calendar and prove sufficient existing read
   access. If either is missing, leave the reader disabled; the owner must select/create and
   populate Public Shows and separately authorize any new consent or credential.
2. Only after a warm sanitized endpoint passes and every in-horizon venue/city display is privately
   approved, deploy the frontend to `50by50-justinleblancmusic` and run the live route/header/privacy
   checks.

Rollback is deliberately asymmetric: for a schedule incident set only
`PUBLIC_EVENTS_ENABLED=false` and restart the owned API; for a frontend incident restore the
captured prior Pages deployment. Retain the additive inquiry schema, never delete a Calendar, and
never reset SQLite.
